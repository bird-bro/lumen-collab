## Intent Lock

- **Change name**: menu-management-web
- **Problem to solve**:
The console menu page (`/system/menus`) is a read-only tree; menu structure could only be
shaped by backend seeds. The backend change `menu-management-api` (see
`openspec/coordination/menu-management.md`) lands the create/update/delete family, so the
page can become the management surface - including authoring the button (F-node)
permission strings that role grants and client/server gates consume.

- **Summary**: upgrade the existing `/system/menus` page from a read-only tree to a
  management table-tree with per-node 新增下级/编辑/删除, a type-aware create/edit dialog
  (button F-nodes author their `perms` strings), the three new API client functions, and
  rejection surfacing - tested at the `vi.mock('@/api/menus')` seam and walked against
  the real backend.
- **In scope**:
  - `src/api/types.ts`: `CreateMenuRequest` / `UpdateMenuRequest` (additive)

## Approved Behavior

<!-- Scenarios confirmed from the change's web-system-console delta -->

1. Tree renders with types and perms: the page shows the directory/menu/button hierarchy
   with each node's type tag and, where present, its `perms` string.
2. Button node CRUD round-trip: create a button under a menu with a perms string, edit
   it, delete it - each calls the documented endpoint and the tree reflects the result.
3. Delete rejection surfaces: deleting a node with live children shows the backend's
   rejection message and the node remains.
4. Dialog guards the parent choice: no `F` nodes selectable as parents; when editing,
   the node itself and its descendants are not selectable.

## Design Constraints

- **Architecture/Decisions**:
- **D1 - `Table` with `treeData`, not the `Tree` component** - stable per-node action
  column (新增下级/编辑/删除); the title cell keeps the type tag + monospace perms tag;
  `defaultExpandAll` on first load.
- **D2 - One dialog, type-aware fields** - `类型` radio drives visibility: 按钮 F → 标题 +
  `perms` (hinted `模块:资源:动作`); 菜单 C / 目录 M → 标题 + `path`/`component`
  (optional for M, mirroring V5 seeds); `icon`/`sort`/`visible` always. Parent
  `TreeSelect` = loaded tree minus `F` nodes minus (when editing) the node's own
  subtree; edit pre-fills from the row.
- **D3 - API client is additive** - `createMenu`/`updateMenu`/`removeMenu` join
  `src/api/menus.ts`; request types in `src/api/types.ts` next to `MenuNode`; existing
  `menuTree` untouched.
- **D4 - Rejections ride the existing error path** - `ApiError.msg` → `messageApi.error`;
  delete confirms via `Popconfirm` before the call.
- **D5 - Affordance gating with `usePerm('system:menu:list')`** - when absent, the
  action column renders nothing; the server gate stays authoritative (roles-page
  symmetry).
- **D6 - Tests stub at the `vi.mock('@/api/menus')` seam** - rewrite
  `menus-page.test.tsx` mirroring the roles-page test structure; runtime requests ride
  the vite proxy to the REAL backend (no mock layer).
- **Technical constraints**:
  - React 18 + TS strict + AntD 5; function components + hooks only
  - Never modify existing shared components or other pages; the page file is
    self-contained
  - `pnpm test` (Vitest) + `pnpm build` type pass must stay green
  - No red as primary color; design tokens over ad-hoc hex
  - Existing-page edit: the `frontend-design` prototype step is skipped (workflow rule)
