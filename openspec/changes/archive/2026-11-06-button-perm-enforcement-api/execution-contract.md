## Intent Lock

- **Change name**: button-perm-enforcement-api
- **Problem to solve**:
The menu-management feature shipped the button-level authoring surface, but the seeds
contain zero F nodes and every console write endpoint is gated only by its page-level
`system:*:list` authority - button permissions are a model, not an enforcement. This
change materializes them server-side: the 22-button F-node seed and method-level
`@PreAuthorize` pins so each console action has its own authority.

- **Summary**: seed 22 button (F) nodes via `V15__button_perm_nodes.sql` (guarded,
  admin auto-granted) and pin the 21 console write endpoints with method-level
  `@PreAuthorize` whose authority is the button perms string - the method annotation
  replaces the class gate for that method (button perm = action authority; page perm =
  visibility), proven by a permission-matrix test.
- **In scope**:
  - `V15__button_perm_nodes.sql` per the coordination inventory (22 F nodes, explicit
    ids, ON CONFLICT guards, role-1 NOT-EXISTS grants, `setval` resync, hand-appliable)
  - Method-level `@PreAuthorize` on the 22 write handlers across 7 controllers
    (UserInfo 3 / Role 4 / Menu 3 / Org 3 / OrgDep 3 / DictCatal 3 / DictDetail 3)
  - Matrix tests in `AuthPermEnforcementTests`: page-only → write denied A0301 + no
    row; button-only → write passes + list denied; admin passes
  - Fixture prefixes registered in the base sweep namespaces
- **Out of scope**:
  - No new endpoints / no request-response shape changes / no session machinery changes
  - No frontend work (`button-perm-enforcement-web` gates by the same inventory strings)
  - No log-family changes (read-only), no menu-model changes, no workstation coupling
  - No `hasAnyAuthority` combined expressions (rejected: degrades to page granularity)

## Approved Behavior

<!-- Scenarios confirmed from the change's specs/auth-rbac delta -->

1. Write endpoint rejects without the button perm: page-only role → `POST /users`
   denied A0301, no user row.
2. Button perm alone authorizes the write: button-only role → write executes; its
   list read stays class-gate denied.
3. Admin sees every button after seeding: 22 F rows exist under their C pages with
   the inventory perms strings; admin login/me perms set contains all of them.
4. Re-running the seed is a no-op: no duplicate menu/role_menu rows.

## Design Constraints

- **Architecture/Decisions**:
- **D1 - One migration, explicit ids, guarded statements** (V5 discipline verbatim:
  explicit F-node ids above the V14 top, `ON CONFLICT (id) DO NOTHING`, role-1 grants
  with the NOT-EXISTS live-binding guard, `setval` resync; every statement a no-op on an
  already-migrated database; hand-appliable on the shared test server first).
- **D2 - Method-level annotation replaces the class gate for that method** (Spring's
  most-specific-annotation resolution): the button node is the ACTION authority, the
  page node stays the VISIBILITY authority via the tree/list gates.
  `hasAnyAuthority('list','create')` rejected - it degrades to page granularity.
- **D3 - Annotation placement is additive-only**: 21 method-level annotations across 7
  controllers; no signatures/bodies change (sign-log-query b2 method-level-pin
  precedent covers annotating existing handlers). Each pinned method carries a
  one-line javadoc pointer to the button-perm model.
- **D4 - Deny tests ride the existing matrix harness** (`AuthPermEnforcementTests`):
  fixture roles via the base-class machinery (run-admin identity, sweep prefixes).
- **D5 - Perms strings live in exactly one source** (the coordination inventory table);
  migration, annotations, tests all quote it; drift is a spec bug, not a code bug.
- **Technical constraints**:
  - JDK 11 + OPS-verified train; build from `lumen-sev/` aggregator
    (`export JAVA_HOME=/Library/Java/JavaVirtualMachines/jdk-11.jdk/Contents/Home`)
  - Errors: deny = `AuthDenyAdvice` A0301 envelope (existing); no new error codes
  - Shared test DB: guarded migration statements; fixture residue swept by the
    base-class `@AfterAll` (register any new prefixes)
