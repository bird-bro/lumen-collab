## Intent Lock

- **Change name**: menu-management-api
- **Problem to solve**:
The menu tree - the permission backbone (role_menu grants, login/me perms set, server-side
`@PreAuthorize` page gates) - can only be shaped by Flyway seeds; `lumen-system` exposes a
single read endpoint (`GET /api/v1/system/menus/tree`). Every IA adjustment therefore needs
a migration, and the button-level (F-node) permission half of the model, though 1:1 ready
since the 随访-recipe foundation, has no authoring surface.

- **Summary**: add a guarded menu CRUD family (POST/PUT/DELETE under
  `/api/v1/system/menus/**`) so admins shape directory/menu/button nodes - including
  F-node perms authoring - without migrations; create auto-grants the admin role, delete
  soft-cleans `role_menu` bindings, moves are cycle-guarded.
- **In scope**:
  - `POST /api/v1/system/menus` (create node, auto-grant admin role, return new id)
  - `PUT /api/v1/system/menus/{id}` (full field update incl. move; cycle + F-leaf + parent-existence guards)
  - `DELETE /api/v1/system/menus/{id}` (live-children rejection; soft delete + soft-clean bindings)
  - Request DTOs (`CreateMenuRequest`/`UpdateMenuRequest`, `@Valid`), new `MenuManageService`
  - Controller grows by new handler methods only; class-level `system:menu:list` gate covers all
  - TDD per task group; whole-reactor verification
- **Out of scope**:
  - No DB migration / no menu-model change; no workstation fields (own future change)
  - No perms format validation or uniqueness; `perms` stored verbatim
  - No drag ordering API (`sort` is a plain field); no icon picker
  - No grant backfill on UPDATE (grants touched on CREATE only)
  - No button-level server-side enforcement (endpoints adopt F-perms incrementally later)
  - No frontend work (that is `menu-management-web`, gated on this change)

## Design Constraints

- **Architecture/Decisions**:
- **D1 - New concrete `MenuManageService`** beside `MenuTreeService` (same package,
  concrete class like `MenuTreeService`; no interface - single-impl family, and the tree
  service already set that precedent). CRUD logic must not blur into the tree assembler;
  `MenuTreeService` stays untouched (read seam for tests unchanged).
- **D2 - Guard computation is in-memory.** One `selectList` of live nodes feeds an
  id→node map + children index; the cycle guard walks the descendant closure of the
  candidate parent; F-leaf and parent-existence guards read the same map. Alternatives:
  recursive SQL CTE (overkill at console scale) or per-level queries (N round-trips).
  The map load also serves create-parent validation and delete child detection with zero
  extra queries.
- **D3 - Auto-grant is a guarded insert, transactional with the node insert.** Create =
  `@Transactional { insert menu; insert role_menu(1, id) with NOT EXISTS live-binding
  guard }` - the guard keeps re-running a create that somehow already has the binding
  idempotent (mirrors the V5 seed discipline). Delete =
  `@Transactional { deleteById (renders UPDATE deleted=1 via @TableLogic);
  roleMenuMapper.delete(by menuId) (same UPDATE shape) }` - the exact cascade shape of
  `RoleServiceImpl.delete`.
- **D4 - Rejections are `BusinessException(ExceptionEnum.ERROR_A0400, <msg>)`** for all
  structural guards (F-parent, cycle, unknown parent, live children on delete). No new
  error-code enums: there is no unique-constraint or state-conflict scenario that would
  warrant an A07xx domain code, and the errors spec keeps A0400 as the
  request-parameter/business-rejection class.
- **D5 - DTOs follow the role family**: `CreateMenuRequest` and `UpdateMenuRequest` as
  separate `@Valid` DTOs (`title` `@NotBlank`; `type` `@Pattern("M|C|F")`; `upId`
  `@NotNull`; others optional), `BeanUtil.copyProperties(request, entity, true)` into the
  entity (house idiom; fields match 1:1). Type flips (M↔C↔F) stay allowed - a plain
  field update; the F-parent guard (not type immutability) protects leaf semantics
  (update to `F` with live children is rejected - the back-door guard).
- **D6 - Controller grows by new handler methods only** (standing "never modify existing
  public methods" rule): `POST`/`PUT /{id}`/`DELETE /{id}` join the existing class;
  the class-level `@PreAuthorize` already covers them. New dependency (`MenuManageService`)
  joins via additive DI (`@Autowired` field, LogController precedent recorded in
  lumen-sev CLAUDE.md 2026-11-05) so the existing constructor stays byte-identical.
- **Technical constraints**:
  - JDK 11 + OPS-verified version train (`lumen-bom`); build from `lumen-sev/` aggregator
    with `export JAVA_HOME=/Library/Java/JavaVirtualMachines/jdk-11.jdk/Contents/Home`
  - Additive-only: `MenuTreeService`, `GET /tree`, existing DTOs/tests untouched
  - Entity Lombok combo `@Data @Builder @AllArgsConstructor @NoArgsConstructor`; Hutool
    utilities preferred (`CollUtil`/`StrUtil`/`BeanUtil.copyProperties(src,dest,true)`)
  - Soft deletes via `EntityBase` `@TableLogic`; audit fields via `MetaObjectConfig`
  - Errors: `BusinessException(ExceptionEnum.ERROR_A0400, msg)`; standard envelope via
    copied `GlobalResponseAdvice`
