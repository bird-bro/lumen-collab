## Intent Lock

- **Change name**: init-backend-skeleton
- **Problem to solve**: `lumen-sev/` contains only role files - no `pom.xml`, no modules,
  nothing to compile. Create the Maven aggregator on the OPS-verified train, the single
  version source, the **OPS `framework`/`common` base modules copied verbatim**, and the
  `lumen-auth` service shell as a **compilable empty shell** that builds and passes tests
  with zero external infrastructure. No business behavior, no Java gateway (nginx is the
  entry), no endpoints.
- **In scope**:
  - `lumen-sev/pom.xml` aggregator + `.mvn` / wrapper as needed
  - `lumen-bom` (OPS managed set 1:1 + lumen-only additions)
  - `framework` + `common` copied verbatim from OPS (five recorded adaptations only)
  - `lumen-auth` service shell (entry point + config + Nacos wiring, port 8081)
  - Build-time and context-load tests that pass with zero infrastructure
- **Out of scope**:
  - **Any Java gateway** - nginx is the unified entry; Spring Cloud Gateway is a future
    cloud-form change
  - `lumen-exam-core`, `lumen-api/{patient-api,integration-api}`, `lumen-patient`,
    `lumen-radiology`, `lumen-integration`, `lumen-us`, `lumen-endo`
  - Any REST endpoint, including health/ping
  - Security wiring beyond the copied classes (token issuance logic belongs to the auth
    feature change)
  - Flyway migrations, entities, mappers, any datasource actually connecting
  - RocketMQ producers/consumers, Sentinel rules, JWT issuing/validation
  - `docker/` compose files and dcm4chee-arc-light
  - CI workflow, GitHub organization registration

## Design Constraints

- **Architecture constraints**: aggregator at `lumen-sev/pom.xml`; monorepo root is not a
  Maven project; services flat under `lumen-sev/`; **no Java gateway** - nginx is the
  unified entry (80/443), SCG reserved for a future cloud change; `framework`/`common`
  copied verbatim from OPS as the shared base of all Servlet services; dual package root
  (`org.birdbro.{framework,common}` copied / `org.birdbro.lumen.*` new); services scan
  `org.birdbro` (OPS `LaunchApplication` habit); shared jars are non-executable
  (`maven-jar-plugin` only, no repackage) and carry no controllers.
- **Interface constraints**: no REST endpoints, no business logic. The copied `framework`
  carries OPS's `GlobalExceptionHandler`/`GlobalResponseAdvice`/`R` envelope code, but no
  endpoint invokes them. This change **modifies the specs** `openspec/specs/{api,errors,data}`
  to adopt OPS's contracts verbatim (user decision 2026-10-29) and implements none of them.
- **Dependency constraints**: pinned train per design D1 - Java 11, Spring Boot 2.5.15,
  Spring Framework BOM 5.3.33, Spring Cloud 2020.0.3, Spring Cloud Alibaba 2021.1,
  MyBatis-Plus `mybatis-plus-boot-starter` 3.5.3.1, Lombok 1.18.30, Hutool 5.8.20, Druid
  1.2.18, PostgreSQL 42.2.18, fastjson2 2.0.38, easyexcel 3.3.2, mapstruct 1.5.5.Final, and
  OPS's remaining managed set 1:1. Libraries OPS does not manage carry no OPS verification
  and stay off every compile path: HAPI HL7v2 2.6.0 (`ca.uhn.hapi`, **not** HAPI FHIR),
  dcm4che 5.35.2, rocketmq-spring-boot-starter 2.2.3. Flyway and Redis are **not** re-pinned
  (already managed by `spring-boot-dependencies`, same as OPS). dcm4che resolves only from
  `https://www.dcm4che.org/maven2` - **absent from Maven Central** (verified 404).
- **Data constraints**: no datasource connects; no Flyway migrations; the operation-log
  table-ownership decision is recorded (per-service schema), not implemented. No committed
  secret in any YAML, including test resources.
- **Verification constraint (binding)**: `docker/` is out of scope, so **every test must
  pass with Nacos, PostgreSQL, Redis, and RocketMQ absent**. Nacos is neutralized in the
  `test` profile via `spring.cloud.nacos.discovery.enabled=false`,
  `spring.cloud.nacos.config.enabled=false`, and bootstrap-mode config (design D3); the
  Redis-conditional adaptation keeps Redis absence harmless.

## Test Obligations

- **Behaviors requiring failing-test-first**:
  - Context load for `lumen-auth` with the `test` profile (task 4.1 - explicitly written
    first, observed failing before the profile exists, then made green). Covers behaviors
    12, 14, 15, and proves Redis-conditional adaptation (behavior 7).
- **Required edge cases**:
  - **All infrastructure absent** during `mvn test` - the primary edge case, not a corner:
    Nacos unreachable and Redis absent must both be non-fatal (behaviors 7, 15).
  - Base modules are non-executable - assert no repackage, no `Main-Class`, no
    `@SpringBootApplication` (behaviors 6, 9).
  - Verbatim guarantee - `diff -r` shows only the four adaptations (behaviors 6, 8).
  - Integration libraries managed but not linked - assert `dependency:tree` carries no
    `org.dcm4che` / HAPI / RocketMQ node (behavior 24).
  - No third-party `<version>` literal outside `lumen-bom` (behaviors 17, 18).
- **Regression-sensitive areas**:
  - **OPS version parity** (behaviors 19-23). A Boot/Cloud/Alibaba mismatch surfaces as
    `NoSuchMethodError` at **runtime**, not compile time - the context-load test is the only
    behavioral guard. If it fails on this verified train, that is a defect to fix, not a
    train to swap.
  - **Verbatim-copy creep** (behaviors 6, 8). "Small fixes" during porting accumulate
    silently; the `diff -r` gates are the guard.
  - Nacos bootstrap neutralization (design D3, Risks). Fallbacks:
    `spring.cloud.service-registry.auto-registration.enabled=false`, then
    `spring.autoconfigure.exclude`.
  - Later changes adding modules must not weaken the `lumen-bom` single-source rule; task
    1.4's grep is the durable check.
- **Characterization**: not applicable - greenfield, no existing un-specced code to baseline
  (the OPS code being copied is the characterization baseline itself).

## Review Gates

- **Mandatory review points**:
  1. **After Batch 1** (aggregator + `lumen-bom`) - blocking. The OPS train and the
     single-version-source rule are inherited by everything downstream; confirm the version
     diff against `ops_sev/pom.xml` is clean for every library OPS manages, the dcm4che
     repository declaration exists, and no module links dcm4che/HAPI/RocketMQ.
  2. **After Batch 2** (verbatim copy) - blocking. Review the `diff -r` result: only the
     five recorded adaptations may differ. This is the byte-faithfulness gate for the whole
     reuse strategy.
  3. **After Batch 3** (auth shell, before Batch 4) - confirm the `test` profile actually
     neutralizes Nacos before the context-load test is written, so Batch 4's red-green cycle
     fails for the right reason.
  4. **After Batch 4** - blocking. This is where Nacos fail-fast and Redis-optional behavior
     are proven. If tests fail, stop and fix per the documented fallbacks rather than
     weakening the test.
  5. **Before archive** - confirm the coordination doc reflects the final versions, ports,
     and package layout.
- **Blocking categories**:
  - Any BOM version that differs from `ops_sev/pom.xml` for a library OPS also manages,
    without a recorded decision (violates the user's verified-compatibility directive and
    `specs/dependency-governance` § Shared Library Version Parity with OPS).
  - Any use of a `spring-boot3`-line starter artifact (`mybatis-plus-spring-boot3-starter`,
    `druid-spring-boot-3-starter`, ...) on this train - those are Boot 3 artifacts and will
    not run on Boot 2.5.15.
  - Any deviation in `framework`/`common` beyond the five recorded adaptations, or any
    renamed/missing class versus OPS (violates `specs/service-topology` § Verbatim Adoption).
  - Any reintroduction of a Java gateway module, or any reactive/webflux dependency entering
    `framework`/`common` (violates the nginx-entry decision and the gateway discipline).
  - Any `@SpringBootApplication` or controller in a shared library (violates behaviors 6, 9,
    10).
  - Any test that requires external infrastructure to pass (violates the binding verification
    constraint).
  - Any third-party `<version>` literal in a child POM (violates behaviors 17, 18).
  - Any committed secret or credential literal (violates behavior 16).
  - Any deferred module created early (`lumen-exam-core`, `lumen-api/*`, `lumen-patient`,
    `lumen-radiology`, `lumen-integration`, `lumen-us`, `lumen-endo`) - violates behavior 5 and the
    Intent Lock.
  - A context-load test "fixed" by deleting assertions or skipping the test rather than
    resolving the Nacos/Redis cause.

## Escalation Rules

- **When to rewind to proposing**: new scope appears; key design assumption wrong; interfaces
  change materially. Specifically for this change:
  - Any desire to move off the OPS train (e.g. to Java 17 / Boot 3.x, or to bump the two
    CVE-flagged OPS versions) - the train is a user-level directive, not an implementation
    detail; a deviation is a new decision to record, and a train change is a new proposal.
  - The verbatim copy proves unbuildable on the pinned train (e.g. a dependency conflict OPS
    never hit because its parent differed) - the reuse strategy is a user-level decision;
    re-plan at the proposing phase.
  - The "boots without infrastructure" criterion proves unachievable (Nacos fail-fast cannot
    be neutralized by any documented fallback) - that would force `docker/` into scope.
  - Anyone requests an endpoint, health check, or a reference auth call chain - new scope;
    the "compilable empty shell" depth was explicitly chosen.
  - A deferred service module is needed to satisfy a requirement here - the foundation subset
    was drawn in the wrong place.
  - The deployment form changes again (gateway reintroduction for hospital, monolith as
    default) - the coordination doc's decisions and the specs assume the current form.
- **When NOT to continue**: contract intent lock no longer matches proposal scope. Concretely:
  do not proceed if the work has drifted into implementing `openspec/specs/{api,errors,data}`
  behavior, writing `docker/` compose files, or building any of the deferred modules - all
  are outside the Intent Lock and belong to their own changes.
