# 医院内网部署形态可行性分析：单体 vs 微服务

> 状态：分析稿，供架构决策。结论会合入 `openspec/coordination/init-project-skeleton.md` 的决策区。
> 决策驱动的硬需求（用户 2026-10-29 确认）：**科室功能升级时不得影响其他科室**（发布隔离），
> 且各科室业务流程存在真实差异（NOTES.md §1.1 状态机 / §1.4 工作台菜单树 / §4 三场景差异）。
> 日期：2026-10-29
>
> **修订（2026-10-29 同日）**：用户澄清业务边界——云端版业务中**只有放射科存在远程诊断**，
> 超声/内镜只能院内现场诊断。因此"云端"不是本地全套的另一种装配，而是**独立产品**（放射科
> 远程诊断/转诊/云胶片），与本地版共享内核库（lumen-bom/framework/common/exam-core/api）。
> 本文涉及"云端"的行均按此理解：指云端**产品**的运行时技术形态，非本地版的部署变体。

## 0. 结论先行

| 部署场景 | 推荐形态 | 中间件 |
|:--|:--|:--|
| **医院内网（默认形态）** | **多服务进程**：按服务拆 JVM + 静态地址发现 + nginx 路由 | nginx + PG + **Nacos（可选，仅作配置中心，推荐开启）** + 可选 Redis |
| 极小站点（乡镇/单科室影像中心） | 模块化单体（同一套代码的合并装配） | 同上，进程更少，接受升级耦合 |
| 云端版（**独立产品**：放射科远程诊断/转诊/云胶片） | 全微服务：SCG + Nacos 注册发现 + RocketMQ；复用内核库 | 另立项提案；us/endo 永不部署到云端 |

**微服务与单体之争是个伪命题**——真正决定医院内网实施成本的是**中间件栈**（注册发现、MQ、网关），
不是 **JVM 进程数**。多进程 + 静态发现同时拿到「发布隔离」和「低实施成本」，是两条约束的唯一交集，
且已被 eis 本地版生产验证多年。Nacos 保留**配置中心**身份（医院形态推荐开启，见 §5.5）——
它解决的"配置集中修改"是真需求；被排除的是它的**服务发现**身份（静态拓扑里无价值）。

## 1. 隔离需求的精确拆解（五维）

「放射科不能影响超声科」在五条不同维度上成立，手段完全不同：

| 维度 | 含义 | 单体内可达成？ | 达成手段 |
|:--|:--|:--|:--|
| **故障隔离**（运行时崩溃/泄漏） | 科室代码崩了，别的科室还能跑 | ❌（共享 JVM） | 进程边界 —— 多进程即达成 |
| **资源隔离**（线程/连接/CPU） | 科室批处理拖慢别的科室 | ✅ | Sentinel 舱壁 + 专用线程池 + `statement_timeout`（进程内） |
| **发布隔离**（升级）★硬需求 | **换科室代码不需要别的科室停机** | ❌ **无解**（换代码=重启宿主进程） | **进程边界** —— 每服务独立 jar 独立重启 |
| 数据隔离 | 科室查询互相拖慢 / 误删 | ⚠️ 部分 | schema 边界 + 权限 + `statement_timeout` |
| 网络风暴隔离 | 设备重连/HL7 洪泛 | ❌ | integration 独立进程（本身就是多进程方案的一部分） |

**舱壁解决 2，解决不了 1 和 3。** 用户确认发布隔离是硬需求后，进程边界不可回避——剩下的选择
只是「进程边界之上要不要再叠中间件」。

## 2. 关键转念：医院实施的重担是中间件，不是进程数

以 lumen v1（放射科单科室）为例，两种"拆法"的实施负担对比：

| 项 | 方案甲：微服务全套 | 方案乙：**多进程 + 配置中心（推荐）** |
|:--|:--|:--|
| 应用进程 | 5 个 JVM | 4 个 JVM（auth / patient / ris / integration；v2 加 us/endo 至 6） |
| Nacos | 注册 + 配置全套 | **仅配置中心**（推荐开启；服务发现仍静态） |
| Java 网关 | Spring Cloud Gateway ×1 | **无**（nginx 承担，见 §5.2） |
| 消息队列 | RocketMQ nameserver + broker ×2 | **无**（HTTP 回调 + 补传，见 §5.3） |
| Redis / PG | 1 / 1 | 1（可选）/ **1 个 PG 实例装 4 个库**（实例≠库，data spec 的 database-per-service 不变） |
| 医院侧总容器 | ≈13 | ≈7（含 PG、dcm4chee、Nacos） |
| 断电自启顺序 | Nacos → 各服务（有依赖链） | compose `restart: unless-stopped` + healthcheck；**Nacos 未起时服务可凭本地配置/快照启动**（§5.5） |
| 信息科要理解的组件 | 注册中心、MQ、网关路由 | Nacos 配置页（UI 改配置）+ nginx（他们最熟） |
| 升级 | 按 jar 替换；受 Nacos/MQ 影响 | 按 jar 替换；与其他服务无关 |
| **发布隔离** | ✅ | ✅（一样达成） |
| **配置集中修改** | ✅ | ✅（Nacos UI + 热更，本就是引入它的理由） |

**方案乙用方案甲 40% 的进程数拿到了同样的发布隔离。** 方案甲多出来的全是中间件的安装、自启、
监控、备份、升级、排障成本——正是医院信息科最薄弱的部分。

### 佐证（自家生产系统，NOTES.md 实测）

- §6.2 安装配置手册：本地版 = **双服务器（16C/64G/2TB ×2）**，sPacs 容器内**双 jar**（eis-api +
  eis-job），宿主机 dpkg 装 MySQL 5.7，Redis 用 Docker，Nginx + dist 前端静态 —— **零注册中心、零 MQ**。
- §6.3 云端版 = K8s + Spring Cloud Alibaba（Nacos/Zuul/Sentinel/Ribbon）+ RabbitMQ —— 中间件全套只在云端出现。
- §2 反面教训 #1：云端=本地 fork 出多分支，BaseResponse 逐字节相同仍在双向漂移 —— 教训是
  **单主干多部署、永不 fork**。多进程零中间件正是"一套代码、两种装配"的落地形态。

## 3. 发布隔离专项：达成路径与两个必须处理的细节

### 3.1 逐服务升级流程（方案乙）

```
放射科升级：systemctl stop lumen-radiology → 换 jar → start
  ├─ lumen-us / lumen-endo：进程未动，零感知
  ├─ 前端：nginx 下 dist 按科室懒加载分块，超声 chunk 未变 → 行为零变化
  └─ 患者端/工作站：ris 不可窗口期 30~60s（nginx 可标记 ris 下线摘除）
```

微服务全套的升级流程与此**完全相同**——这就是说：方案乙在发布隔离上不输方案甲。

### 3.2 细节一：共享内核 exam-core 会牵连所有科室（必须钉版本）

`lumen-radiology`、`lumen-us`、`lumen-endo` 都依赖 `lumen-exam-core`。单体形态下内核升级 = 全科室
一起动，发布隔离破功。多进程形态的解法是 **Maven 版本钉住**：各服务独立构建，ris 停留在
exam-core 1.0、us 用 1.1，互不牵连；内核 API 按语义化版本演进，破坏性变更走新版本号。
配套纪律（写入 spec）：**科室差异不进内核**——流程骨架与扩展点在 exam-core，检查项目/报告模板/
设备对接差异在科室服务或配置数据（NOTES §2 教训 #5：医院差异全部建模为数据，代码零 if）。

### 3.3 细节二：契约兼容窗口（服务间调用的版本偏斜）

升级 ris 时，patient/integration 的 Feign 契约必须兼容。纪律：`lumen-api` 契约**只加不改**，
破坏性变更新增接口版本；消费方未升级期间旧接口继续可用。这是多进程形态新增的、微服务全套同样
存在的成本（方案乙没有豁免权），但量级很小——服务间契约就 patient-api / integration-api 两个。

## 4. 公平起见：微服务全套在医院内网的真实故障面

拆分不是只带来隔离，也**新增**了一类单体没有的故障模式。方案乙刻意避开的正是这一层：

| 微服务全套新增的故障模式 | 医院内网的现实影响 |
|:--|:--|
| 注册中心单点：Nacos 挂了，新实例上/下线感知失效（本地缓存列表可撑一阵，配置热更停摆） | 医院没有实例动态变化，Nacos 的价值≈0，风险>0 |
| MQ 积压 / 消息丢失 / 重复消费 | 需要监控面板 + 消费幂等 + 补传机制，信息科没有 MQ 排障经验 |
| Feign 超时/重试雪崩 | 需要全局超时预算设计；医院负载下收益趋零 |
| 断电恢复依赖链 | Nacos 先起、服务后起，自启脚本多一层顺序 |
| 升级顺序约束 | 中间件版本与服务版本有兼容矩阵要维护 |

医院内网拓扑是**静态的**：4~6 个固定 IP、无弹性伸缩、实例地址几乎不变。注册中心解决的问题是
"实例动态变化"，这个问题在医院不存在——所以方案乙用配置文件里的静态地址替代它，是消除成本而非
阉割功能。

## 5. 中间件替代与保留策略（全部在现有列车内）

### 5.1 静态服务发现（替代 Nacos 的注册发现身份）

Spring Cloud 自带 `SimpleDiscoveryClient`，无需任何注册中心：

```yaml
spring:
  cloud:
    discovery:
      client:
        simple:
          instances:
            lumen-patient:
              - uri: http://192.168.10.21:8082
            lumen-integration:
              - uri: http://192.168.10.22:8083
```

OpenFeign + LoadBalancer 照常工作（Cloud 2020.0.x 内置）。医院 IP 规划好后写进安装配置，
变更 = 改配置文件重启对应服务。**列车不变、代码不变、只是发现方式从动态变静态。**

### 5.2 nginx 承担网关路径约定（替代 Spring Cloud Gateway）

api spec 的「Gateway Path Convention」是 `/api/v1/<service>/**`——nginx 用 path 路由即可
实现同一契约：

```nginx
location /api/v1/ris/          { proxy_pass http://ris_cluster/; }        # 双实例 upstream
location /api/v1/patient/      { proxy_pass http://patient/; }
location /api/v1/auth/         { proxy_pass http://auth/; }
```

前端 SPA 的 `/api/v1` 统一打到 nginx。**含义与影响**：lumen-gateway 模块保留在代码库中
（云端形态使用），医院形态用 nginx——后续 change 需对 api spec 的 Gateway Path Convention
做一条 MODIFIED 增量，把「经 lumen-gateway」放宽为「经平台网关入口（Spring Cloud Gateway 或
nginx 路由）」，路径约定本身不变。

### 5.3 跨进程事件：HTTP 回调 + 补传（替代 RocketMQ）

MPPS「检查完成」→ 更新 ris 检查单，是唯一的跨进程状态流。零中间件做法：
integration 收到 MPPS → 调 ris 的内部回调接口（静态地址）→ 失败落本地队列（integration 自带
持久化）→ 恢复后补传；ris 侧幂等（按 MPPS UID 去重）。医院规模下事件量级极小（每天千级），
这条链路不需要 MQ 的吞吐，需要的是**不丢**——本地队列 + 补传即达成。
`EventPublisher` 抽象接口保留：本地实现 = HTTP 回调适配器，未来云端实现 = RocketMQ 事务消息。

### 5.4 保留不动的进程内隔离手段

Sentinel 舱壁、专用线程池（OPS `ThreadPoolConfig`/`AsyncManager` 模式）、`statement_timeout`
仍然全部适用——资源隔离在多进程形态内继续做，双保险。

### 5.5 Nacos 回归：仅作配置中心（可选组件，推荐开启）

用户决策（2026-10-29）：医院内网保留 Nacos，理由是**配置集中修改**——信息科在 Web UI 上改
配置、热更新、看历史一键回滚，好过 SSH 到 N 台机器 vim + 重启；且 OPS 生产已在用（bootstrap.yaml），
信息科有既有经验。采纳，但以**三条护栏**把它设计成"坏而不灾"：

1. **本地兜底原则**：每个服务的本地 `application.yml` 必须能独立启动（DB 地址、端口、
   Nacos 地址本身等"连接类"配置在本地；Nacos 只做**覆盖**——可调参数、功能开关、科室级业务参数）。
   禁止"只有 Nacos 里才有"的启动必需配置。
2. **快照兜底**：Nacos 客户端自带本地快照（最后一次拉到的配置落盘）。Nacos 进程挂掉时，运行中
   服务零影响（配置热更停摆而已），**重启中的服务用最后一次快照照常启动**。即：Nacos 故障的
   影响面 = "暂时改不了配置"，不是"服务起不来"。
3. **热更范围限定**：`@RefreshScope` 只标注真正的运行时可调项（超时阈值、限流阈值、功能开关、
   报告模板参数）；连接池大小、DB 地址这类改动仍走"改配置 + 计划重启"的变更流程，避免热更
   半生效状态。

配套约定：
- **服务发现保持静态**（§5.1 不变）——Nacos 只当配置中心。这样"Nacos 挂"对运行中的服务间调用
  零影响；发现链路里没有它的位置。
- Nacos standalone **容器化**（compose 内），derby 数据卷纳入备份；版本在列车内
  （SCA 2021.1 → Nacos client 1.4.x，服务端配 1.4.x 对应版）。
- 安装包提供两个 profile：`with-nacos`（默认）/ `without-nacos`（极小站点），服务代码零差异。

### 5.6 Docker 交付形态（医院内网标准，用户确认 2026-10-29）

医院内网**统一用 Linux + Docker compose 部署**（eis 本地版已验证此路径，NOTES §6.2）。多服务进程
在 Docker 语义下 = **一个模块一个 jar、一个 jar 一个容器**：

| 容器 | 内容 | 关键配置 |
|:--|:--|:--|
| `nginx` | 统一入口：`/api/v1/<service>/**` 路由 + 前端静态 + 双实例 upstream | 挂载 conf 与 dist |
| `nacos` | **仅配置中心**（standalone） | derby 数据卷持久化 |
| `lumen-auth` / `lumen-patient` / `lumen-radiology` / … | 每模块一个 fat jar | `SPRING_PROFILES_ACTIVE=hospital`（静态发现 profile） |
| `lumen-integration` | 设备侧唯一进程 | 映射 MWL/HL7 端口给设备网；**补传队列持久化卷** |
| `postgres` / `dcm4chee` / `redis`（可选） | 数据与 PACS 本体 | 数据卷 |

构建与分发的分工：**构建一体，部署分开**——`mvn package` 在聚合工程一次产出全部 jar，每 jar
构建一个镜像（共用 JRE 11 基础镜像）。内网无镜像仓库时的分发：制作机 `docker save` 出 tar →
医院 `docker load` → `docker compose up -d --no-deps lumen-radiology`。

**Docker 额外白送的两层隔离**：
- `mem_limit`（cgroups）：某服务 OOM 只杀自己的容器，compose 自动拉起，其他容器无感——进程级
  故障隔离天然成立；
- **升级影响面**：`up -d --no-deps <service>` 只重建该容器，其余容器（含 nginx 后面的其他科室）
  全程未动——发布隔离落到一条命令。

与 eis 的关键差异：eis 本地版是"单容器双 jar"（eis-api + eis-job 同容器，升级必须整容器重启、
两 jar 耦合）；lumen 改为"**一容器一 jar**"，升级隔离才真正成立。

## 6. 负载测算（估算值，量级判断用）

| 量 | 估算 | 依据/说明 |
|:--|:--|:--|
| 中型三甲放射科日检查量 | 800~1500 人次 | 行业常识量级 |
| 峰值并发工作站用户（全院 RIS 相关） | 50~100 | 登记/审核/报告岗位总数上限 |
| 业务后端峰值 QPS | ~500-1000 | 每操作触发 2~5 个查询的放大系数 |
| 单 JVM 承载（8C16G, Tomcat 400 线程） | 富余 5~10 倍 | RIS 请求均为小 JSON；影像流量走 dcm4chee/阅片器，不经过业务后端 |
| 各服务 JVM 基础内存 | 512MB~1GB 堆 | Spring Boot 2.5 实际运行经验值 |

结论：**负载量级上单科室一个 JVM 极度富余**，多进程的总内存（4×~1GB ≈ 4GB）与单体
（1×4GB）相当。微服务的横向扩展能力在"单院区、机器有限"的约束下没有用武之地——没有第二台
机器让它扩。

## 7. 分场景决策矩阵与升级触发信号

| 场景 | 形态 | 理由 |
|:--|:--|:--|
| 单院区医院（默认） | **多进程（Nacos 仅配置中心）** | 发布隔离 ✅ + 配置集中改 ✅ + 实施成本低 |
| 极小站点（乡镇/单机房 1 台服务器） | 模块化单体（launch 合并装配，代码同一套） | 省到极致；接受升级耦合（本来也是一次全升） |
| 多院区 / 区域影像中心 / 云端 | 全微服务（Gateway+Nacos 注册发现+RocketMQ） | 动态实例、统一入口、跨院事件流 |
| 科室数量增长（us/endo 上线） | 不变，加进程 | 每科室一个 jar，模式不变 |

**从低形态升到高形态的触发信号**（出现才升级，不预先升级）：
1. 实例地址开始动态变化（弹性扩缩/跨机房漂移）→ 引入 Nacos **注册发现**（配置中心已在用）；
2. 需要统一入口做鉴权/限流/灰度/协议转换 → 引入 Spring Cloud Gateway；
3. 跨进程事件量级上到每秒百级、或需要事务消息/延迟消息（检查超时催办）→ 引入 RocketMQ。

反向（云端 → 医院打包）同样成立：同一套代码，静态发现 profile + nginx 部署包。

## 8. 残余风险登记（多进程零中间件形态）

| 风险 | 缓解 |
|:--|:--|
| ris 升级窗口内放射业务中断 30~60s | nginx 摘除标记 + 夜间窗口；双实例滚动可再压缩 |
| exam-core 升级牵连科室 | §3.2 版本钉住 + 内核只加不改的语义化版本纪律 |
| 服务间契约版本偏斜 | §3.3 契约只加不改 + 消费方兼容窗口 |
| HTTP 回调丢事件 | integration 本地持久化队列 + 补传 + ris 幂等（MPPS UID 去重） |
| Nacos 不可用导致服务无法重启 | 本地兜底配置 + 客户端快照（§5.5）——影响面收敛为"暂时改不了配置" |
| 热更配置半生效 | §5.5 护栏 3：`@RefreshScope` 只标运行时可调项，连接类配置走变更+重启 |
| 静态配置漂移（IP 改了配置没改） | Nacos UI 集中修改（单一修改点）+ 启动时对每个静态地址做可达性探测并写日志 |
| 部署描述从 1 份变多份 | 一套 docker-compose 模板 + 每服务一个镜像；离线分发用 `docker save/load` tar 或院内私有 registry——脚本工作量，不是运维复杂度 |
